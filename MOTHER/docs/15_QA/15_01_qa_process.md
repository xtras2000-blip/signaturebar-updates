# 15_01 QA Process

MOTHER의 QA는 2단으로 구성된다: (1) 문서 QA — 저장소의 문서·데이터가 규격을 지키는지 머지 전에 검사, (2) 플레이 QA — 빌드가 감정 목표(01_04)를 실제로 달성하는지 검사. 게임오버가 없으므로(D-002) "클리어 가능 여부" 테스트는 존재하지 않으며, 감정 정합성이 합격 기준을 대체한다.

## 1. 1단 — 문서 QA (자동 린트 + 리뷰)

대상: `MOTHER/docs/` 전체와 콘텐츠 JSON. 체크 실패 시 처리: **REJECT**(머지 불가) 또는 **WARN**(리뷰어 판단).

| check_id | 검사 | 규칙 | 실패 시 | 근거 |
|---|---|---|---|---|
| `DOC-01` | 메커닉 문서 7섹션 | 02~14 디렉터리의 메커닉 문서에 Purpose / Variables / State Machine / UI / Database / JSON / QA H2가 모두 존재하는가 | REJECT | PROJECT_RULES |
| `DOC-02` | emotion_tags 필수 | 모든 event 정의(문서 예시 포함)에 비어 있지 않은 `emotion_tags` 배열이 있는가. 태그 값은 01_04 §1의 13종 안에 있는가 | REJECT (자동) | D-005 |
| `DOC-03` | 회수 계획 필수 | `memory_tag`를 기록하는 모든 `choice`에 회수 계획(`callback_plan`: 회수 챕터 + 회수 이벤트/엔딩 참조)이 있는가 | REJECT | Pillar 4 "회수 계획 없는 선택지는 만들지 않는다" |
| `DOC-04` | 용어집 정합 | 문서·JSON의 식별자가 00_04 등록 표기와 일치하는가. 미등록 신규 식별자는 00_04에 먼저 등록됐는가 | REJECT | 00_04 §3 |
| `DOC-05` | 캐논 수치 정합 | 핵심 수치 5종·성격 축 4종 외의 스탯 식별자 사용 여부. 초기값이 D-009와 일치하는가 | REJECT | D-003, D-008, D-009 |
| `DOC-06` | 성격 축 상한 | 단일 choice의 성격 축 effects 절대값 ≤ 3 | REJECT (자동) | 03_01, Pillar 4 |
| `DOC-07` | H1·분량 규격 | H1이 `# {디렉터리번호}_{문서번호} {영문 제목}` 형식인가. 파일이 80~180줄 범위인가 | WARN | STYLE_GUIDE |
| `DOC-08` | 결정 로그 추적 | 필러와 상충하거나 캐논을 바꾸는 서술이 DECISION_LOG 항목을 인용하는가 | WARN | 01_02 |

- 실행 시점: PR 생성 시 자동(DOC-02, 05, 06은 스크립트 린트), 나머지는 리뷰 체크리스트. 자동 린트의 이벤트 스키마 기준은 13_JSON 소유.
- 리젝된 문서는 수정 커밋으로만 해소한다. 예외 승인은 DECISION_LOG 등재가 선행 조건.

## 2. 2단 — 플레이 QA

### 2.1 감정 설문 (01_04 §4)

- 대상: 챕터 단위 빌드. 외부 테스터 최소 12인(부 타깃 비게이머 4인 이상 포함, 01_03).
- 방법: 챕터 플레이 직후, 감정 형용사 12개(목표 감정 + 교란 항목) 중 복수 선택 문항 제시.
- **통과 기준: 해당 챕터 목표 감정 형용사 선택률 60% 이상.** 챕터별 목표 형용사는 01_04 §1의 핵심·보조 감정을 그대로 사용한다.

| check_id | 챕터 | 통과 조건 (선택률 ≥ 60%) |
|---|---|---|
| `PLAY-E1` | CH1 | 압도됨 계열 + (경이 또는 고립감) |
| `PLAY-E2` | CH2 | 벅참 계열 + (소진 또는 보람) |
| `PLAY-E3` | CH3 | 서툰 자부심 계열 + (걱정 또는 비교 불안) |
| `PLAY-E4` | CH4 | 미안함 계열 + 화해 |
| `PLAY-E5` | CH5 | 떠나보냄 계열 + (뿌듯함 또는 상실감) |

- 불합격 시: 수치 밸런스 조정보다 연출 우선순위(01_04 §2 — 아이 행동 변화 > 일상 변주 > 대사 > 음악 > 수치)의 상위 수단부터 보강한다.

### 2.2 회귀 테스트 순서

빌드마다 아래 순서로 수행한다. 하위 단계는 상위 단계 통과를 전제로 한다.

| 순서 | check_id | 범위 | 내용 |
|---|---|---|---|
| 1 | `PLAY-R1` | 스모크 | 새 세이브 → CH1 3일 진행 → 저장/로드. 크래시·데이터 손실 없음 |
| 2 | `PLAY-R2` | 시스템 체크리스트 | 15_02의 QA-02~QA-14 전 항목 실행 |
| 3 | `PLAY-R3` | 챕터 통과 | 각 챕터 시작~종료 1회씩. 챕터 전환·마일스톤 이벤트 발생 확인 |
| 4 | `PLAY-R4` | 극단 플레이 | 전 수치 방치 런 / selfcare 전용 런 각 1회 — 게임오버 미발생(D-002), 서사적 결과만 발생 확인 |
| 5 | `PLAY-R5` | 회수 검증 | memory_tag 기록 후 해당 callback_plan 이벤트가 후속 챕터에서 실제 발생하는지 샘플 10건 추적 |
| 6 | `PLAY-E1~E5` | 감정 설문 | §2.1. 마일스톤 빌드에서만 수행 |

## 3. 운용 절차

### 3.1 문서 QA 워크플로우

1. 작성자가 PR 생성 → 자동 린트(DOC-02, 05, 06) 실행.
2. 자동 통과 시 리뷰어가 DOC-01, 03, 04, 07, 08을 체크리스트로 확인.
3. REJECT 항목은 라벨 `qa-reject`로 표시하고 사유에 check_id를 명기한다(예: "DOC-03: `mem_ch2_daycare_wait`의 callback_plan 부재").
4. 전 항목 통과 시에만 머지. 예외는 DECISION_LOG 신규 항목으로만 성립한다.

### 3.2 결함 기록 규격

| 필드 | 내용 |
|---|---|
| check_id | 위반 항목 (DOC-nn / PLAY-xx / QA-nn-nn) |
| severity | `blocker`(캐논·필러 위반) / `major`(기능 오동작) / `minor`(표기·연출) |
| repro | 세이브 파일 + 재현 절차. 플레이 QA는 14_AI 결정 로그·`stat_delta_log`(03_01) 첨부 |
| owner_doc | 수정 소유 문서 번호(예: 07_EVENT). 코드가 아닌 문서가 원인이면 문서를 먼저 고친다 |

- 감정 설문 불합격(PLAY-E*)은 결함이 아니라 디자인 이슈로 분류하고, 원인 분석에 반드시 01_04 §2 우선순위 역순 점검("수치를 보여주고 있지 않은가"부터)을 포함한다.

## 4. check_id 명명 규칙

- 문서 QA: `DOC-{nn}` / 플레이 QA: `PLAY-{구분}{n}` (E=감정, R=회귀).
- 시스템 체크리스트(15_02): `QA-{디렉터리번호}-{nn}` 예: `QA-07-02`.
- 각 메커닉 문서 내부 QA 표의 TC 식별자(예: TB-01, ST-01)는 해당 문서 소유이며, 15_02는 이를 시스템 단위로 묶어 참조한다.
- check_id는 재사용·재번호 부여 금지. 폐기된 항목은 표에서 삭제하지 않고 `(retired)` 표기로 남겨 리포트 이력 호환을 유지한다.
- 신규 체크 항목은 근거(캐논 계약·DECISION_LOG·필러 중 하나)를 명기해야 등록할 수 있다.
